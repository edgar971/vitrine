Status: **draft for review** (2026-10-17). Nothing here is implemented. When a feature ships, its
normative text moves into [`spec.md`](../spec.md) (and [`security.md`](../security.md) for a new
threat or control) in the same change, and the matching section here is deleted.

The keywords **MUST**, **MUST NOT**, **SHOULD** and **MAY** are used as in the spec. "Spec § n"
means a section of the 0.1 spec.

Three findings from the research change the shape of the list:

- **Per-artifact expiry already exists.** `expires_in` sets `expires_at`; views return 410 and the
  sweep deletes the artifact (spec § 4.3). The gap is scheduled *unpublish*, so § 4 covers only
  that.
- **Markdown already renders,** and an `index.md` entry opens rendered (spec § 7.2). The gap is
  GitHub-flavoured syntax and front matter.
- **Zip upload was rejected on purpose** (research § 2: zip bombs and zip slip). The real gap is
  narrower: an agent with only a shell and an upload URL cannot send a folder in one `PUT`, and
  there is no CLI. § 3 and § 6 close that, and § 3 needs an ADR because it reverses a recorded
  decision.

Several features share one `meta.json` bump (schema 2, § 10.1), the new `/api` routes (§ 6.2) and
the new configuration keys (§ 10.3). Ship them in the order in § 11.

What vitrine takes from them, and where it deliberately differs:

- **Passcode:** everyone does it; nobody documents a design that survives vitrine's sandbox (§ 1.2
  explains why a cookie does not). vitrine unlocks into a short-lived signed URL instead.
- **Separate content origin** (demiplane, Bauta): vitrine already isolates agent HTML with a CSP
  sandbox and an opaque origin; the dashboard is the first vitrine page that holds a session, so
  § 5 recommends its own hostname.
- **JSX through a CDN** (artifacts): accepted for viewers' browsers, opt-in, with the transpiler
  served by vitrine itself, so the server still makes no outbound request (security T11).
- **Root-absolute assets break under `/a/{id}/`** (artifacts documents the same trap): § 3.4.

## 1. Viewer passcode

**Problem.** A private link is a bearer capability. Links get forwarded, pasted into tickets, and
fetched by chat unfurl bots (Slackbot, Discordbot, Telegram) that render a preview for everyone in
the channel. A passcode adds a second factor the link alone does not carry.

### 1.1 Model

- A passcode belongs to the **artifact**, not to one link. Setting it takes effect on every
  existing private link and on the public URL immediately, because narrowing must not wait for
  links to expire. (Per-link passcodes are an open question, § 12.)
- `meta.json` gains `passcode`: `null`, or `{"hash", "salt", "n", "r", "p", "generation"}`. The
  hash is `hashlib.scrypt` (standard library; `n = 2¹⁵, r = 8, p = 1`), computed in a worker
  thread. `generation` increments on every set or clear.
- A passcode is either **generated** by the server (10 Crockford base32 characters from a CSPRNG,
  shown as `xxxxx-xxxxx`, 50 bits; the hyphen and case are ignored on entry) or **supplied** by
  the caller (8 to 128 characters). A generated passcode is returned **once** and never stored in
  clear.
- The passcode **MUST NOT** appear in the audit log, the access log, metrics or any error.

### 1.2 Unlocking

A cookie does not work here. Agent HTML runs in an opaque origin (spec § 7.2), so the browser
treats every subresource request a page makes as cross-site: a `SameSite=Lax` or `Strict` cookie
is not sent with the page's own images, scripts and styles, and a multi-file artifact would break.
`SameSite=None` would work but is sent on every cross-site request. vitrine already solved the
same problem for version pinning by keeping state in one path segment (spec § 7.1), so unlock does
the same:

```
GET  /s/{sig}/…            passcode set → 401, the unlock form (vitrine's own page, no content)
POST /s/{sig}/unlock       passcode=…   → 303 Location: /s/{usig}/…   (the path asked for)
GET  /s/{usig}/…           serves the artifact, relative links keep working
```

```
usig body = "unlocked" "|" id "|" expires_unix "|" link_epoch "|" passcode_generation
```

- `unlocked` is a new signed kind (spec § 3): it **MUST NOT** verify as `view` or the reverse.
- Its expiry is the earlier of `unlock_ttl` (*configurable*, default `12h`) and the expiry of the
  link it was unlocked from.
- A `usig` whose generation is not the artifact's current one is an invalid link (404). Changing
  or clearing the passcode therefore ends every unlocked session, and so does any epoch bump.
- On the public URL, `GET /a/{id}/` shows the same form and `POST /a/{id}/unlock` redirects to
  `/s/{usig}/`.
- An unlocked URL is itself a bearer capability, short-lived. That is the residual risk (§ 1.5).
- Recording the choice of a signed URL over a cookie is **ADR 0006**.

**The form page** is vitrine's, not the agent's: no title, no file names, nothing from the
artifact, so a link holder learns only that a passcode is needed. It carries
`Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self';
frame-ancestors 'none'`, `no-store` and the other view headers.

**The `POST`:**

- body `application/x-www-form-urlencoded`, at most 1 KiB, one field `passcode`;
- a foreign `Origin` returns 403 (spec § 7.4 rules);
- a wrong passcode returns the form again with 401 and one generic message;
- an unlock on an artifact without a passcode redirects to the link itself; a bad signature or an
  expired artifact behaves exactly like the `GET` would (404 / 410).

### 1.3 Brute force

- New bucket `rate_unlock`, keyed by **artifact and source IP**, default `10/m`, counting failed
  attempts only, plus a per-artifact ceiling `rate_unlock_artifact`, default `100/h`.
- Exhausted: 429 with `Retry-After`, and the passcode is **not** checked, so timing reveals
  nothing.
- The per-artifact ceiling lets someone who already holds the link lock out the other viewers for
  an hour. That is accepted: it needs the link, and the owner can rotate it.

### 1.4 Interface

| Tool | Parameters | Result | Scope |
|---|---|---|---|
| `artifact_set_passcode` | `id`; `passcode?` (omitted: generate); `clear = false` | `{id, passcode?, url}`. `passcode` only when generated. | `vitrine:share`; clearing on a **public** artifact also needs the gate (below) |

- **Setting** narrows the audience, so it needs no gate.
- **Clearing** on a public artifact widens it from "link and passcode" to "anyone with the link",
  so it **MUST** pass the public gate (spec § 6) with a confirmation naming the title and saying
  the passcode will be removed. On a private artifact, clearing needs only `vitrine:share`.
- Annotations: `readOnlyHint` false, `destructiveHint` true (it locks out viewers),
  `idempotentHint` false, `openWorldHint` false.
- The description **MUST** tell the model to give the passcode to the user separately from the
  link.
- HTTP: `POST /api/artifacts/{id}/passcode` (§ 6.2), same rules; clearing on a public artifact is
  refused with 403, like every other gated change over HTTP (spec § 4.4).
- `artifact_get` and `artifact_list` rows gain `passcode: bool`.
- Audit: `passcode_set` (`generated: bool`) and `passcode_cleared` (`gate` when public).
- Metric: `vitrine_unlock_total{outcome="ok"|"wrong"|"rate_limited"}`.

### 1.5 Security

New threat row: **T22, a forwarded or unfurled link exposes a private artifact.** Control: the
passcode, the unlock rate limits, and `usig` bound to the passcode generation. Residual (new
**R7**): the generated passcode passes through the MCP transcript, because the agent must tell the
user; the unlocked URL is forwardable for up to `unlock_ttl`; and the passcode is only as strong
as a supplied one is chosen, which is why generation is the default.

Specs that would fail without it: `it_shows_the_form_instead_of_the_content`,
`it_never_serves_content_for_a_wrong_passcode`, `it_ends_unlocked_urls_when_the_passcode_changes`,
`it_refuses_to_clear_a_public_passcode_without_the_gate`, `it_never_logs_the_passcode`, and in
Chromium `it_loads_the_pages_own_assets_after_unlocking`.

## 2. Markdown and JSX/TSX rendering

### 2.1 Markdown (already rendered; extend the syntax)

Today: CommonMark with raw HTML disabled, entry included. Proposed:

- Enable the GitHub-flavoured extensions built into `markdown-it-py`: **tables** and
  **strikethrough** (no new dependency).
- Add `mdit-py-plugins` for **task lists**, **footnotes** and **front matter**. Front matter is
  parsed as YAML-like `key: value` lines only (no YAML library); `title` becomes the page
  `<title>`, everything else is dropped from the output.
- Heading anchors (`id` from a slug of the heading text) so `#section` links work.
- Raw HTML **MUST** stay disabled. Mermaid and syntax highlighting stay on the roadmap: both need
  either a heavy dependency (Pygments) or a CDN.

No new configuration: the `md` renderer improves in place. Behaviour change for upgraders: a table
that rendered as text now renders as a table.

### 2.2 JSX/TSX (new renderer, opt-in)

A single React component, the way agents already write them for hosted artifacts.

**Input.** A `.jsx` or `.tsx` file whose module has a default export that is a component. The
entry rule (spec § 4.3) applies unchanged, so `App.tsx` as the only file opens rendered.

**Output.** The renderer returns an HTML shell, served under the same sandbox CSP as every
renderer (spec § 7.2):

```html
<!doctype html><meta charset="utf-8"><title>{escaped filename}</title>
<script type="importmap">{"imports": {"react": "…", "react-dom/client": "…", …}}</script>
<script type="text/plain" id="vitrine-source">{source, HTML-escaped}</script>
<div id="root"></div>
<script src="/_vitrine/jsx/{version}/sucrase.js" integrity="sha384-…" crossorigin></script>
<script type="module" src="/_vitrine/jsx/{version}/mount.js" integrity="sha384-…" crossorigin></script>
```

- The **source is inlined**, never fetched: the page runs in an opaque origin, so fetching its own
  file would be a cross-origin request that `/s/` must not answer with CORS.
- The **transpiler** (a browser build of Sucrase, MIT, JSX + TypeScript only; Babel standalone
  if no maintained browser build exists, to verify) and a 30-line mount
  script are **vendored in the wheel** and served by vitrine at `/_vitrine/…` (a new `PUBLIC`
  route: immutable, `Cache-Control: public, max-age=31536000, immutable`,
  `Access-Control-Allow-Origin: *`, Subresource Integrity on every reference). vitrine itself
  still makes no outbound request (T11).
- **Imports** resolve through the import map:
  - `react`, `react-dom`, `react-dom/client` and `react/jsx-runtime`, pinned to versions recorded
    in the release, from `jsx_cdn`;
  - any other bare specifier resolves to `{jsx_cdn}{name}?external=react,react-dom` only when
    `jsx_any_package = true`; otherwise the mount script shows "package not available: name";
  - relative imports (`./Chart`) are refused with a visible message in 0.3: a component that
    spans files should be published as a built site (§ 3).
- **Tailwind:** `jsx_tailwind = true` adds the Tailwind Play CDN script, since agents assume it.
- Errors (syntax, missing default export, a throw while rendering) render as an escaped message in
  the page, never a blank screen.
- `?raw=1` serves the source as `text/plain`. `jsx` and `tsx` join the content-type allowlist as
  `text/plain; charset=utf-8`, so they are viewable rather than forced to download.

**Configuration** (§ 10.3): `jsx` is **not** in the default `renderers` list, because it makes
viewers' browsers load code from a third party. `jsx_cdn` defaults to `https://esm.sh/`;
`jsx_any_package` defaults to `false`; `jsx_tailwind` to `true`.

**Security.** No new server-side control: the shell is renderer output under the same sandbox.
What changes is that a viewer's browser now trusts `jsx_cdn` for every JSX page; operators who
care can point it at a self-hosted esm.sh. Note in security.md, beside T7: agent HTML could
already load any script (the CSP restricts the origin, not the sources), so this widens the
default trust set, not what an artifact can do.

Specs: `it_renders_a_default_export`, `it_escapes_a_closing_script_tag_in_the_source`,
`it_refuses_a_relative_import_with_a_message`, `it_keeps_the_sandbox_on_the_shell`, in Chromium
`it_mounts_the_component_in_an_opaque_origin`.

## 3. Zip site upload

**Problem.** A built site (`dist/`) can be published today as multipart with one part per file,
which the Hermes plugin and `curl -F` do. An agent that only has a shell and an upload URL (spec
§ 7.3) cannot: the URL takes one file. `zip -r - dist | curl -T - "$put_url"` is the one-liner
agents reach for.

This reverses research § 2 ("Zip bundles: brings in zip-bomb and zip-slip classes"), so it needs
**ADR 0007** stating the controls below as the condition.

### 3.1 Interface

- `PUT /u/{sig}?unpack=zip` (beside the existing unsigned `filename` and `title`).
- `POST /api/artifacts` and `PUT /api/artifacts/{id}`: exactly one `file` part of type
  `application/zip` plus the field `unpack=zip`.
- `artifact_upload_url` gains `unpack?: "zip"`; its `curl` line becomes the zip one-liner.
- An unpacked archive **replaces** the version's files (a site is a whole), unless `merge=true`.
- The result gains `files` (count) and `skipped` (count of entries dropped by § 3.2).

### 3.2 Controls

The archive is staged to `tmp/` under the existing body limit (`max_upload`), then read from its
central directory. Every rule fails the **whole** upload with 400 or 413, nothing written:

| Rule | Why |
|---|---|
| Entries ≤ `max_files`; directory entries ignored | Count limit as for multipart |
| Each entry is inflated **streaming**, and the running total ≤ `max_artifact`; declared sizes are not trusted | Zip bombs lie in the header |
| Per-entry compression ratio ≤ `unpack_max_ratio` (default `200`) once the entry passes 1 MiB | Defence in depth: stop a bomb before the total limit |
| Methods `stored` and `deflate` only; encrypted entries refused | Bounded decoder surface |
| Each name passes the spec § 4.3 path rule, after stripping one top-level folder shared by **every** entry | `zip -r site.zip dist` works; `../`, absolute and backslash names are refused (zip slip) |
| Symlink entries (Unix mode `S_IFLNK` in the external attributes) refused | Symlink escape |
| Duplicate paths after the strip refused | One archive, one meaning |
| Names must be UTF-8 (flag bit 11) or ASCII | No codepage guessing |
| Archives inside the archive are stored as files, never unpacked | One level only |
| Entries under `__MACOSX/` and names with a segment starting with `.` are **skipped**, counted in `skipped` | Finder and Git junk; the same rule the Hermes plugin applies to folders |

Quota and the `quota` check run on the inflated bytes, as for any version.

### 3.3 SPA fallback

`meta.json` gains `fallback`: `null` or a path in the version. A request under the artifact for a
missing file serves the fallback: with status **404** when it is named `404.html`, else **200**
(the single-page-app case, `index.html`). It never applies to a path with an extension in the
asset set (`js css png …`), so a missing script fails loudly instead of returning HTML. Set with
`fallback?` on create, update and the `/api` forms; it **MUST** name a file in the version.

### 3.4 Root-absolute URLs

A site built for `/` requests `/assets/index.js`, which is outside `/a/{id}/` and 404s. vitrine
cannot rewrite agent HTML safely, so the fix is documented, not engineered: build with a relative
base (`vite build --base=./`, `"homepage": "."` for CRA, `trailingSlash` + `assetPrefix: "./"` for
static Next). The upload result **SHOULD** warn (`warnings: ["root-absolute asset URLs in
index.html"]`) when the entry HTML references `src="/` or `href="/`.

Specs: one `it_refuses_*` per row of § 3.2 (`…_a_dot_dot_entry`, `…_a_symlink_entry`,
`…_an_archive_that_inflates_past_max_artifact`, `…_a_lying_size_header`), plus
`it_strips_the_shared_top_level_folder` and `it_serves_the_fallback_for_a_missing_route`.

## 4. Scheduled unpublish

**What exists:** `expires_in` on create and update sets `expires_at`; after it, views return 410
and the sweep deletes the artifact. That is "auto-delete", and it stays as is.

**New: `public_until`.** A public artifact reverts to private at a set time and keeps existing.

- `meta.json` gains `public_until`: `null` or a timestamp.
- `artifact_set_visibility(id, "public", public_for?)`: a duration. The gate confirmation **MUST**
  name the date ("public until 24 Oct"). Without `public_for`, the artifact is public with no end,
  unless `public_ttl_max` is set.
- `public_ttl_max` (*configurable*, default `off`): when set, every public artifact gets
  `public_until` no later than now + this, and `public_for` above it is clamped. Operators who
  want nothing public forever set it once.
- **Enforced at request time, not only by the sweep.** `/a/{id}/` **MUST** answer 404 once
  `public_until` has passed, even before the sweep runs (sweeps are hourly by default).
- The sweep then makes it private: `visibility = private`, `public_until = null`, link epoch + 1,
  audit `visibility_changed` with `client = "@sweep"`, `gate = "scheduled"` (new value).
- Moving `public_until` later, or clearing it, widens exposure, so it is only possible through
  `artifact_set_visibility(public, …)` and the gate. Making it private early is
  `artifact_set_visibility(private)`, as today.
- `artifact_get` and list rows gain `public_until`.

Specs: `it_stops_serving_the_public_url_at_public_until_before_the_sweep`,
`it_revokes_private_links_when_the_sweep_unpublishes`, `it_names_the_end_date_in_the_confirmation`.

## 5. Web dashboard

**The security question first.** The dashboard is the first vitrine page that holds a logged-in
session in a browser, and it would let a person change visibility. Two consequences:

1. It is the natural home for the **out-of-band approval** already on the roadmap (security R2):
   a human approving a publish in a browser, where an agent holding a `vitrine:publish` token
   cannot answer for them.
2. It **MUST NOT** be possible to log in with a client token alone, or R2 comes back: an agent
   that reads its own token could drive the dashboard over HTTP and approve its own publish.

So it ships in two phases.

### 5.1 Phase 1: inspect and narrow (0.4)

- `dashboard = false` by default. When on, served at `admin_base_url` if set (**SHOULD** be its
  own hostname, like demiplane's split origins), else at `{base}/_admin/`. Refused at startup on a
  non-loopback `http://` base, because the session cookie needs `Secure`.
- **Login: passkeys (WebAuthn) with user verification.** Enrolment by the operator from a shell:
  `mcp-vitrine admin enroll <label>` prints a single-use enrolment URL (10 minutes). Credentials
  live in `data_dir/admin/credentials.json` (public keys only). Dependency: `webauthn`. A
  password-only login is the alternative (§ 12).
- **Session:** cookie `__Host-vitrine_admin`, `Secure; HttpOnly; SameSite=Strict; Path=/`, 12 h,
  HMAC-signed with a key derived from `secret`, stateless. Every mutation is a `POST` that checks
  `Origin`, `Sec-Fetch-Site: same-origin` and a per-session CSRF token.
- **Pages:** the list (filters and search from § 7, facets by project), one artifact (versions,
  links, passcode state, view counts from § 8, its audit history), and the audit log.
- **Actions, narrowing only:** mint a private link, revoke links, set or rotate the passcode, edit
  title/tags/project (§ 7.2), **make private**, delete. No action makes anything public.
- **Rendering:** server-side HTML, no build step, `Content-Security-Policy: default-src 'self';
  frame-ancestors 'none'; form-action 'self'`. Titles, tags, notes and file names are
  agent-written and **MUST** be escaped (a new XSS surface; the dashboard is not sandboxed).
  Artifact content is never shown inline: "open" mints a private link in a new tab.
- **Audit:** `client = "@admin:<label>"`. New route class `SESSION` in `ROUTE_ACCESS`.

### 5.2 Phase 2: the approval surface

When an elicitation-incapable client calls `artifact_set_visibility(public)`, instead of
`unsupported` the tool returns `{status: "pending", approve_at: "<admin url>"}` and records a
pending request (artifact, version, client, expiry 24 h). The human approves in the dashboard with
a fresh passkey assertion; the write still has to find the version shown (spec § 6.1). This adds
a second decision source to `PublicGate` (`gate = "dashboard"`), so it amends ADR 0002 and closes
R2. It is specified fully when phase 1 has shipped.

## 6. Client CLI and `/api` parity

### 6.1 The `vitrine` command

`mcp-vitrine` is the operator's command: it reads `data_dir` and needs `VITRINE_SECRET`. A client
command is a different tool with a different trust level, so the wheel installs a second script,
**`vitrine`**, that only speaks HTTP to `/api` with a token.

| Command | Does | Scope |
|---|---|---|
| `vitrine publish PATH… [--title] [--entry] [--tag …] [--project] [--expires] [--note] [--ref] [--zip] [--fallback]` | Files and folders as one multipart create (folders by the Hermes plugin's rules: relative paths, hidden files and symlinks skipped); `--zip` sends one archive (§ 3) | write |
| `vitrine publish PATH… --update ID [--merge]` | A new version of an existing artifact | write |
| `vitrine list [--query] [--tag] [--project] [--visibility] [--limit] [--all]` | Listing; `--all` follows cursors | read |
| `vitrine get ID` | Metadata, files, views (§ 8) | read |
| `vitrine link ID [--ttl] [--label]` | A fresh private link | share |
| `vitrine revoke ID` | Revoke private links | share |
| `vitrine passcode ID [--set VALUE \| --clear]` | § 1; generates when neither is given | share |
| `vitrine tag ID [--add …] [--remove …] [--project] [--title]` | § 7.2 | write |
| `vitrine delete ID [--yes]` | Asks unless `--yes` or stdin is not a terminal (then refuses without `--yes`) | write |
| `vitrine open ID` | `link`, then the system browser | share |

- **Configuration:** `VITRINE_URL` and `VITRINE_TOKEN` (the variables spec § 8.1 already reserves
  for clients), or `--url` and `--token-file PATH`. A token **MUST NOT** be accepted as an
  argument: argv is visible to every user on the host through `ps`.
- **Output:** the URL alone on stdout, messages on stderr, so `url=$(vitrine publish r.html)`
  works; `--json` prints the API response.
- **No `--public`.** The one path to public stays the MCP gate. `publish` says the link is
  private; there is nothing to flag.
- Exit codes as spec § 9: 0, 1 failed, 2 usage or configuration.
- Implemented with `httpx` (already installed by FastMCP) in `mcp_vitrine/client/`, which imports
  nothing from `services`, `storage` or `web` (a new import-linter contract), so it could be split
  into its own package later.

### 6.2 New `/api` routes

The CLI and the dashboard need these, and they make `/api` a complete alternative to MCP for
everything except going public:

| Method and path | Auth | Behaviour |
|---|---|---|
| `GET /api/artifacts/{id}` | bearer, `read` | `artifact_get` |
| `DELETE /api/artifacts/{id}` | bearer, `write` | `artifact_delete` |
| `PATCH /api/artifacts/{id}` | bearer, `write` | JSON `{title?, tags?, add_tags?, remove_tags?, project?}` (§ 7.2). Any other key, `visibility` included, is 400. |
| `POST /api/artifacts/{id}/links` | bearer, `share` | JSON `{ttl?, label?}` → `{url, expires_at}` |
| `POST /api/artifacts/{id}/revoke` | bearer, `share` | `{id, link_epoch}` |
| `POST /api/artifacts/{id}/passcode` | bearer, `share` | JSON `{passcode?, clear?}` (§ 1.4) |

Each is classified `BEARER` in `ROUTE_ACCESS`, spends the same bucket as its tool, and is audited
like it. The route-table spec covers them for free.

## 7. Projects, tags and search

### 7.1 Projects

- `meta.json` gains `project`: `null` or a name `[a-z0-9][a-z0-9_.-]{0,63}`. One per artifact; tags
  stay many.
- `project?` on create, the `/api` forms, `artifact_list` and `vitrine list`.
- `artifact_list(facets = true)` adds `{projects: {name: count}, tags: {name: count}}` over the
  whole matching set, so the dashboard and agents can show the groups without paging everything.

### 7.2 Metadata without a version

Today `artifact_update(title=…)` writes a new version, and on a public artifact that goes through
the gate. Retitling or retagging changes nothing a viewer sees: title, tags and project are only
shown in listings and prompts, never served under `/a/` or `/s/`. So:

- New tool `artifact_set_meta(id, title?, tags?, add_tags?, remove_tags?, project?)`, scope
  `vitrine:write`, idempotent. It rewrites `meta.json` only: no version, **no gate**, no epoch
  change.
- Audit `metadata_changed` with `fields: ["tags", "project"]`: the names of what changed, never
  the values (titles stay out of the audit log, spec § 11.3).
- `artifact_update` keeps its behaviour; its description points to `artifact_set_meta` for
  metadata-only changes.

### 7.3 Search

- `query` becomes **terms**: split on whitespace, each term must match (AND), case-insensitively,
  as a substring of the title, a tag, the project, a version note or the entry file name.
- New filters: `updated_after?`, `passcode?` (bool), `expiring_within?` (duration).
- `sort = updated` (default) | `created` | `title`.
- **No content search** in this proposal. `list` scans `meta.json` (design § 5, fine to about 10⁴
  artifacts); scanning files would not be, and an index is a `Store` concern. Recorded as a
  roadmap item.

## 8. View counts and access logs

**Constraint.** The audit log is fsync'd per state change and never holds content (spec § 11.3).
Views are not state changes and can be a flood (`rate_views` is 1200/m per IP), so they get their
own, cheaper record. "Who" cannot mean a person: viewers are anonymous. It can mean *which link*,
and "a distinct visitor" without storing an IP.

### 8.1 Modes

`view_log` (*configurable*): `off` | `counts` (default) | `links`.

- **`counts`:** per artifact, per hour, per route (`a` | `s`): `views`, `visitors`, `bots`.
- **`links`:** the same, plus per link. Private links carry a link id: a new body form
  `"view" "|" id "|" expires "|" epoch "|" lid`, with `lid` 8 random bytes (b64url). Links without
  a `lid` keep verifying and are counted under `"lid": null`. `artifact_link` gains `label?` (at
  most 64 characters, for "sent to finance"), kept with the `lid` and expiry in `meta.json`
  `links` (the newest 100). With link ids, **per-link revoke** becomes possible:
  `artifact_revoke_links(id, link?)` adds the `lid` to `revoked_links`.

### 8.2 What counts

- A view is a `GET` answered 2xx whose path is the **entry** (or a renderer page). Assets do not
  count, so a page with 30 images is one view. `HEAD`, `Range` requests and `Sec-Purpose:
  prefetch` do not count. A request refused by a rate limit does not count.
- A **visitor** is `HMAC(hour_key, ip | user-agent)`, where `hour_key` is random, held in memory and
  replaced every hour. Only the count of distinct values is stored, so **no IP address or user
  agent reaches disk**.
- A **bot** is a user agent matching a short list of link unfurlers (Slackbot,
  Discordbot, TelegramBot, WhatsApp, Twitterbot, facebookexternalhit, LinkedInBot). Counted
  separately: "the link was unfurled in a chat" is a signal the owner wants, and it should not
  inflate views.

### 8.3 Storage

- Counters live in memory and are flushed every 60 s and at shutdown to
  `views/<YYYY-MM>.jsonl`, one line per (hour, artifact, route[, lid]):
  `{"hour":"2026-10-17T14:00Z","artifact":"…","route":"s","lid":"…","views":12,"visitors":3,"bots":1}`.
- No fsync per view. A crash loses up to a minute of counts: views are telemetry, not audit, and
  the spec says so.
- Disk grows with (artifacts × hours viewed), not with requests, so a flood costs memory for one
  counter, not disk.
- `view_retention` (default `90d`) deletes whole months, like `audit_retention`. Deleting an
  artifact leaves its counts until retention; they hold only ids.

### 8.4 Reading

- `artifact_get` gains `views: {total, visitors, bots, first_viewed_at, last_viewed_at, links:
  [{lid, label, views, first_viewed_at, last_viewed_at, expires_at}]}`.
- Resource `artifact://{id}/views`: hourly series for the last 30 days.
- `vitrine get ID`, the dashboard artifact page, and `mcp-vitrine views [--id] [--since]` for the
  operator.
- Metrics keep their rule (no ids): `vitrine_views_total` gains `kind = "view" | "bot"`.

Specs: `it_counts_one_view_for_a_page_and_its_assets`, `it_never_writes_an_ip_address`,
`it_counts_an_unfurler_as_a_bot`, `it_attributes_a_view_to_its_link`,
`it_refuses_a_link_whose_lid_was_revoked`.

## 9. Notifications

"Tell me when someone opens the link, or when something is made public."

### 9.1 Over MCP (no outbound traffic)

- Resource subscriptions on `artifact://{id}/views` and `artifact://{id}/history`: the server sends
  `notifications/resources/updated` on the **first view** of each link and on every visibility
  change. A connected agent can then say "finance opened the report".
- Only reaches clients that are connected and subscribed. **To verify:** FastMCP 4.1's support
  for `resources/subscribe` on a `LocalProvider` (research § 3 does not cover it).

### 9.2 Webhook (opt-in, changes T11)

- `notify_url` (environment only, since the URL often carries a token), events `notify_events`
  (default `published, unpublished, first_view, expired`).
- Payload: `{event, artifact, ts, link?: lid, gate?}`. Ids only, the same rule as the audit log,
  so it can go to ntfy, a Home Assistant webhook or a chat bot without leaking titles.
- `X-Vitrine-Signature: sha256=HMAC(key derived from secret, body)`.
- Delivery in a background task: 5 s timeout, 3 retries with backoff, an in-memory queue of 1000
  (oldest dropped, counted in `vitrine_notify_dropped_total`). It never delays the request that
  caused it.
- **Security:** T11 says vitrine never makes outbound requests. With `notify_url` set it makes
  exactly one kind, to one configured host, carrying ids only. That needs **ADR 0009** and an
  edit to T11 and to the Kubernetes example's egress policy (an allow rule for that host, off by
  default).

## 12. Open questions

1. **Passcode per artifact or per link?** Per artifact is proposed: it is simpler, it protects the
   public URL too, and it takes effect on links already sent. Per link (a passcode inside the link
   record) fits "different passcode for each recipient", and becomes cheap once `links` mode
   (§ 8) stores link records.
2. **Bauta's emailed one-time code** needs outbound mail (SMTP), which T11 forbids today. Out of
   scope unless § 9.2's egress decision is taken.
3. **JSX: vendored transpiler and CDN imports** (proposed) or a server-side build? A server-side
   build needs a Node or esbuild binary in the image, which vitrine does not ship today.
4. **Dashboard login: passkeys** (proposed, proves a human is present, one new dependency) or an
   operator passphrase hash in the environment (no dependency, but anything that can read the
   server's environment can log in)?
5. **`view_log` default:** `counts` (proposed) or `off`? `counts` stores no personal data, but
   it is a new kind of record that operators may not expect.
6. **Webhook at all?** MCP notifications cover a connected agent; a webhook covers the phone. It
   is the only feature here that changes T11.
